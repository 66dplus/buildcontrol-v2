# Сценарии Telegram-агента директора

Что директор может спросить у бота прямо сейчас. Все запросы — на русском, в свободной форме. Агент сам найдёт `project_id` по части названия (`list_projects`) и сгенерирует SQL к локальной SQLite через `query_database` — см. промт в [db/schema_docs.py](../db/schema_docs.py).

Бот отвечает только из проверенного `chat_id` (`TELEGRAM_DIRECTOR_CHAT_IDS` в `.env`).

---

## 1. Проекты

| Что спросить | Что вернёт |
|---|---|
| «Какие у меня проекты?» / «Список объектов» | id + название всех неархивных проектов |

База: [projects](../db/schema_docs.py#L11) (`projects.is_archived = 0`).

---

## 2. Бюджет

| Что спросить | Что вернёт |
|---|---|
| «Бюджет по Питеру» / «Сколько освоено по ЖК ПИТЕР?» | план vs факт по этапам + общий итог |
| «По каким этапам перерасход бюджета?» | этапы, где `fact_total > plan_total` |
| «Какой план по ФОТ на Гатчине?» | `labor_plan` по проекту |

База: [budget_phases](../db/schema_docs.py#L58) с `COALESCE` через компоненты (materials_plan + labor_plan + equipment_plan), потому что `total_plan` может быть NULL/0.

Формат: `30 000 ₽ из 600 000 ₽ (5%)`. Жирный + ⚠️ только при перерасходе.

---

## 3. Задачи

| Что спросить | Что вернёт |
|---|---|
| «Какие задачи в работе по Питеру?» | задачи с `stage_name NOT IN ('Новая','Завершена')` (промежуточные стадии — пользовательские: «Выполняются», «В работе» и т.п.), плюс резервная эвристика для NULL: `completion_pct > 0 AND < 100` ИЛИ `date_start_actual` есть без `date_end_actual` |
| «Просроченные задачи по Гатчине» | `date_end_plan < сегодня AND completion_pct < 100` |
| «Что планируется на ближайшие 30 дней?» | `date_start_plan` или `date_end_plan` в окне сегодня…+30 дней |
| «Сколько готово по этапу фундамент?» | средний `completion_pct` по фазе |

База: [tasks](../db/schema_docs.py#L15). После апр-2026 `stage_name` зеркалится из Bitrix-канбана прорабским отчётом и при одноразовом ресинхе через `scripts/migrate_bitrix_to_sqlite.py`. Для старых задач может быть NULL — промт говорит LLM в этом случае использовать `completion_pct` / `date_*_actual`.

---

## 4. Закупки и материалы

| Что спросить | Что вернёт |
|---|---|
| «Что куплено по Березкам?» | `qty_bought` по всем материалам |
| «Сколько израсходовано цемента на Питере?» | `qty_consumed` (НЕ `qty_bought`) |
| «Остатки на складе по Гатчине» | `qty_stock = qty_bought − qty_consumed` |
| «Какая средняя цена покупки топлива?» | `price_actual` (средневзвешенная) |
| «Сколько активных проектов используют арматуру?» | `COUNT DISTINCT project_id` по материалу |

База: [materials](../db/schema_docs.py#L28). Промт жёстко разводит `qty_bought` ≠ `qty_consumed` ≠ `qty_stock` — агент не должен путать «куплено» и «потрачено».

---

## 5. Перерасходы (тройная проверка)

Когда директор спрашивает «есть ли перерасход?», агент по правилам промта проверяет **все три** источника:

| Сигнал | Источник | SQL-условие |
|---|---|---|
| Цена в конкретной заявке выше плана | `purchase_requests.items_json` через `json_each` | `price > price_plan` |
| Средневзвешенная цена материала выше плана | `materials.price_actual` | `price_actual > price_plan` |
| Расход материала опережает % выполнения задач | `materials` ⨯ `tasks` | `consumed_pct > task_done_pct + 15%` |

Любое превышение `> 0.1%` — это перерасход. Не округляется. Формат ответа из промта:

> «По цене есть перерасход: {overspend_rub} ₽. В запланированном бюджете стоимость составляет {plan_total} ₽, а закупка идёт на {actual_total} ₽ (+{dev_pct}%).»

Что **не** перерасход: `purchase_requests.status = 'rejected'` (это решение согласующего, не цена).

---

## 6. Сводка по проекту

«Сводка / отчёт / статус по Питеру» — агент по умолчанию не выдаёт «полный отчёт по всему», правило промта:

> «Отвечай ТОЛЬКО на то, о чём спросили. Вопрос о закупках → только закупки. Вопрос о бюджете → только бюджет. Вопрос о задачах → только задачи и сроки.»

Если нужен общий обзор — сформулируй явно: «Дай сводку по бюджету, задачам и закупкам по Питеру», и агент пройдётся по трём блокам.

---

## 7. Заявки на согласование

| Что спросить | Что вернёт |
|---|---|
| «Какие заявки ждут согласования?» | `purchase_requests.status = 'pending'` по всем проектам |
| «Когда последняя одобренная заявка по Гатчине?» | `MAX(resolved_at)` где `status = 'approved'` |
| «Кто отказал по последней заявке Питера?» | `actor` + `approver_comment` |

База: [purchase_requests](../db/schema_docs.py#L71). Утренний дайджест (`app/notifications/digest.py`) уже шлёт сводку pending-заявок в 09:00 МСК — через бот можно посмотреть в любой момент.

---

## 8. Чего агент пока **не умеет**

- Менять данные. Тулсет = `list_projects` + `query_database` (только SELECT). Никаких write-операций.
- Прикладывать графики/файлы. Только текст HTML.
- Помнить контекст между запросами. Каждый вопрос — независимый.
- Отвечать пользователям вне `TELEGRAM_DIRECTOR_CHAT_IDS`.
- Запрашивать данные напрямую из Bitrix24 — читает только локальную SQLite. Если данные в Bitrix новее — нужен ресинк через [scripts/migrate_bitrix_to_sqlite.py](../scripts/migrate_bitrix_to_sqlite.py).

---

## Расширение

Чтобы агент начал отвечать на новый класс вопросов:
1. Если данные уже в SQLite — добавить пример SQL в `SCHEMA_DOCS` ([db/schema_docs.py](../db/schema_docs.py)). Кода писать не надо.
2. Если данных в SQLite нет — сначала зеркалить из Bitrix (расширить `scripts/migrate_bitrix_to_sqlite.py` + точку обновления в `app/webhook_handler.py`).
3. Если нужна write-операция — зарегистрировать новый тул в `TOOL_REGISTRY` в [app/telegram_agent.py](../app/telegram_agent.py) (схема + async handler).
