# Сценарии агента директора

Что директор может спросить у агента прямо сейчас. Все запросы — на русском, в свободной форме. Агент сам найдёт `project_id` через `list_projects` и сгенерирует SQL через `query_database` — см. схему в [db/schema_docs.py](../db/schema_docs.py).

---

## Поверхности

| Поверхность | Инструменты | Подтверждение записи |
|---|---|---|
| Telegram-бот | все 6 инструментов (2 read + 4 write) | нет — выполняется сразу |
| Веб-чат (браузер) | все 6 инструментов (2 read + 4 write) | да — UI-диалог перед write-операцией |

Оба канала используют один и тот же код агента: `app.agent.core.run_agent()`.

Telegram-бот отвечает только из проверенного `chat_id` (`TELEGRAM_DIRECTOR_CHAT_IDS` в `.env`).

---

## 1. Проекты

| Что спросить | Что вернёт |
|---|---|
| «Какие у меня проекты?» / «Список объектов» | id + название всех неархивных проектов |

База: `projects.is_archived = 0`.

---

## 2. Бюджет

| Что спросить | Что вернёт |
|---|---|
| «Бюджет по Питеру» / «Сколько освоено по ЖК ПИТЕР?» | план vs факт по этапам + общий итог |
| «По каким этапам перерасход бюджета?» | этапы, где `fact_total > plan_total` |
| «Какой план по ФОТ на Гатчине?» | `labor_plan` по проекту |

База: `budget_phases` с `COALESCE` через компоненты (materials_plan + labor_plan + equipment_plan), потому что `total_plan` может быть NULL/0.

Формат: `30 000 ₽ из 600 000 ₽ (5%)`. Жирный + ⚠️ только при перерасходе.

---

## 3. Задачи — чтение

| Что спросить | Что вернёт |
|---|---|
| «Какие задачи в работе по Питеру?» | задачи с промежуточной стадией канбана + резервная эвристика по `completion_pct` |
| «Просроченные задачи по Гатчине» | `date_end_plan < сегодня AND completion_pct < 100` |
| «Что планируется на ближайшие 30 дней?» | `date_start_plan` или `date_end_plan` в окне сегодня…+30 дней |
| «Сколько готово по этапу фундамент?» | средний `completion_pct` по фазе |

База: `tasks`. Для старых задач `stage_name` может быть NULL — агент использует `completion_pct` / `date_*_actual` как резервный сигнал.

---

## 4. Задачи — запись (write-инструменты)

Агент может не только читать, но и вносить изменения в Bitrix24.

| Что сказать | Инструмент | Что произойдёт |
|---|---|---|
| «Создай задачу "Ревизия склада" в проекте Питер ответственному Алексею» | `create_task` | Задача создаётся в Bitrix24 и зеркалится в SQLite |
| «Назначь Алексея на задачу 456» | `assign_user` | `RESPONSIBLE_ID` задачи 456 обновляется в Bitrix24 |
| «Переведи задачу 456 на стадию "В работе"» | `move_task_stage` | Задача перемещается в указанную колонку канбана |
| «Добавь комментарий к задаче 456: выявлен дефицит цемента» | `add_comment` | Комментарий добавляется в чат задачи Bitrix24 |

**Telegram:** write-инструменты выполняются немедленно без подтверждения — агент опишет в ответе, что было сделано.  
**Веб-чат:** UI показывает диалог подтверждения перед выполнением write-операции.

Каждая write-операция автоматически логируется в таблицу `audit_log`.

## 5. Закупки и материалы

| Что спросить | Что вернёт |
|---|---|
| «Что куплено по Березкам?» | `qty_bought` по всем материалам |
| «Сколько израсходовано цемента на Питере?» | `qty_consumed` (НЕ `qty_bought`) |
| «Остатки на складе по Гатчине» | `qty_stock = qty_bought − qty_consumed` |
| «Какая средняя цена покупки топлива?» | `price_actual` (средневзвешенная) |

База: `materials`. Агент строго разводит `qty_bought` ≠ `qty_consumed` ≠ `qty_stock`.

---

## 6. Перерасходы (тройная проверка)

Когда директор спрашивает «есть ли перерасход?», агент проверяет **все три** источника:

| Сигнал | Источник | SQL-условие |
|---|---|---|
| Цена в конкретной заявке выше плана | `purchase_requests.items_json` через `json_each` | `price > price_plan` |
| Средневзвешенная цена материала выше плана | `materials.price_actual` | `price_actual > price_plan` |
| Расход материала опережает % выполнения задач | `materials` ⨯ `tasks` | `consumed_pct > task_done_pct + 15%` |

Любое превышение `> 0.1%` — это перерасход. Не округляется. Формат:

> «По цене есть перерасход: {overspend_rub} ₽. В запланированном бюджете стоимость составляет {plan_total} ₽, а закупка идёт на {actual_total} ₽ (+{dev_pct}%).»

Что **не** перерасход: `purchase_requests.status = 'rejected'` (это решение согласующего, не цена).

---

## 7. Заявки на согласование

| Что спросить | Что вернёт |
|---|---|
| «Какие заявки ждут согласования?» | `purchase_requests.status = 'pending'` по всем проектам |
| «Когда последняя одобренная заявка по Гатчине?» | `MAX(resolved_at)` где `status = 'approved'` |
| «Кто отказал по последней заявке Питера?» | `actor` + `approver_comment` |

---

## 8. Ограничения

- Прикладывать графики/файлы — только текст.
- Помнить контекст между запросами — каждый вопрос независимый.
- Отвечать пользователям вне `TELEGRAM_DIRECTOR_CHAT_IDS` (Telegram).
- Запрашивать данные напрямую из Bitrix24 — читает только локальную SQLite. Если данные в Bitrix новее — нужен ресинк.
- **Telegram**: write-инструменты выполняются без UI-подтверждения (по дизайну).

---

## Расширение

Все инструменты живут в `app/agent/tools/`. Чтобы добавить новый:

1. **Только чтение** (аналитика): создать файл в `app/agent/tools/`, декорировать `@_register({..., "write": False})`. Обновить `SCHEMA_DOCS` в `db/schema_docs.py` если нужны подсказки для LLM.

2. **Запись в Bitrix24**: создать файл в `app/agent/tools/`, использовать паттерн `_tool_inner(client, ...)` + `@_register({..., "write": True})`. Зарегистрировать в `app/agent/core.py` (добавить `import app.agent.tools.new_tool`). Write-операции автоматически логируются в `audit_log`.

3. Импортировать новый модуль в `app/agent/core.py` чтобы он зарегистрировался при запуске.
